System Overview &amp; Purpose IWSTGS (Intelligent Work Simulation and Task Guidance System) is an adaptive, project-based learning platform designed to simulate authentic professional software engineering work environments. Its primary objective is to provide learners with realistic, role-contextualised work experience through structured task sequences, intelligent performance feedback, and competency-aware progression. 1.1 Primary Objectives (In Priority Order) The system is designed to optimise the following objectives in priority order: Priority Objective Rationale 1 Realistic Simulation Experience Justifies all structural decisions: project-based design, role enrolment, context fidelity, and task design rooted in real software delivery. 2 Scalable System Design Without scalability, the system cannot reach enough learners to deliver value at meaningful volume. 3 Evaluation Accuracy Refinable over time through learner submissions, feedback, and AI recommendations; not a fixed, pre-solved problem. 1.2 System Scope Simulates software engineering project delivery using realistic project scenarios with multiple collaborating roles. Enrolls learners into professional roles and assigns tasks consistent with those roles. Adapts task complexity, guidance level, and scenario realism to learner competency in real time. Evaluates learner submissions across multiple competence dimensions and produces a detailed competency profile. Builds on foundational university and institutional knowledge while extending it toward industry readiness. 2. Learner Entry &amp; Classification Model Learners are classified at entry into one of two broad categories. This classification determines the starting rank, initial task complexity, and diagnostic approach. 2.1 Entry Categories Category Criteria Inexperienced No professional work history in software engineering, or less than 1 year of experience. Experienced 1 or more years of professional software engineering experience in a defined role. 2.2 Experienced Learner Constraints For experienced learners, role enrolment is filtered by years of experience. Certain senior or lead roles are inaccessible to learners with insufficient years. This prevents misrepresentation and ensures task difficulty is appropriate for the learner&apos;s claimed background. Rule: Role Gating by Experience Experienced learners declare their years of experience at enrolment. The system restricts available roles based on declared experience thresholds. Role thresholds are defined per-role in the system configuration. A learner cannot manually override role access restrictions. 2.3 Mismatch Detection The system actively monitors for mismatches between a learner&apos;s declared entry category and their observable submission quality: Underestimation (Inexperienced path, strong submissions): If a learner&apos;s core task submissions consistently exceed the expected junior-level answer families, the system flags the mismatch. It may auto-escalate rank or surface a prompt asking the learner if they wish to continue at a higher level. If the learner declines escalation, the system records the flag and gradually escalates task difficulty naturally within their chosen path rather than keeping tasks static, avoiding monotony. Overestimation (Experienced path, repeated failures): If a learner fails beyond a defined failure threshold on core tasks, the system initiates a rank review process (see Section 4.4: Diagnostic Consequence Tasks) and may de-escalate the learner&apos;s rank. Rank is a living attribute, not a fixed entry-point label. 3. Rank Architecture Rank in IWSTGS is not a simple flat label. It is a multi-tiered attribute on the learner profile that governs task assignment, complexity calibration, consequence task difficulty, and final profile interpretation. 3.1 Rank Tiers Rank Sub-levels Description Junior Junior-1, Junior-2, Junior-3 Entry-level competency. Tasks have low complexity. Architectural decisions are not assigned. Guidance is high. Mid Mid-1, Mid-2, Mid-3 Intermediate competency. Tasks introduce moderate complexity and cross-component dependencies. Senior Senior-1, Senior-2, Senior-3 Advanced competency. High complexity, low autonomy scaffolding withdrawn. Architectural tasks included. 3.2 Rank as a Living Attribute Rank is dynamically updated throughout a learner&apos;s engagement with the system: Initial rank is assigned after the diagnostic evaluation phase. Rank can escalate based on consistent strong performance across core tasks. Rank can de-escalate based on persistent failure patterns, triggering a rank review. Sub-level progression within a rank tier happens more frequently and with lower performance thresholds than cross-tier promotions. 3.3 Rank Influence on Task Assignment Rank Level Task Assignment Effect Junior-1 to Junior-2 Low complexity only. High guidance. No system design tasks. No architectural decision tasks. Junior-3 to Mid-1 Low-to-medium complexity introduced. Guidance begins reducing. Some cross-component dependency tasks. Mid-2 to Mid-3 Medium complexity standard. Moderate guidance. Component interaction and integration tasks included. Senior-1+ High complexity available. Minimal guidance. Architectural and distributed system tasks unlocked. 4. Diagnostic &amp; Assessment Framework The system offers multiple pathways for assigning an initial rank. The platform operator may configure which method is active. All methods are designed to measure reasoning ability and decision-making quality, not just technical recall or stack familiarity. 4.1 Diagnostic Pathway Options Interview-Style Assessment: A structured series of questions presented in conversation format that probe reasoning, trade-off awareness, and conceptual understanding. Assessment Tasks: A set of defined tasks administered before project enrolment. Evaluated according to standard task criteria. Diagnostic Scenario (Recommended): A mid-complexity scenario is presented to the learner. Tasks within this scenario are set to mid-level complexity, autonomy, and context fidelity by default — not adjusted at runtime to the learner&apos;s rank, because rank has not yet been determined. 4.2 Diagnostic Scenario Design Diagnostic Scenario Rules Complexity, Autonomy, and Context Fidelity are fixed at MID level — not runtime-adjusted. The scenario must be stack-agnostic: the core challenge is evaluable regardless of technology choice. Evaluation criteria target reasoning and decision-making, not familiarity with a specific pattern. Tasks must require trade-off decisions so that surface-level implementers are distinguishable from reasoning-capable learners. A strong submission that justifies decisions is the key observable indicator of genuine competency. 4.3 Post-Diagnostic Rank Assignment After the diagnostic phase, the system aggregates submission quality across all diagnostic tasks and maps the result to an initial rank tier and sub-level. This rank is written to the learner profile as the starting rank. 4.4 Diagnostic Consequence Tasks (Runtime-Generated) If a learner enters via the experienced path and fails beyond the defined failure threshold on core tasks, the system triggers a diagnostic consequence task. These differ from standard consequence tasks: Diagnostic consequence tasks are generated by the AIMediation at runtime, not pre-defined. They use a complexity-agnostic, autonomy-agnostic, context-agnostic template that can be applied to any observed area of failure. The AIMediation fills in the task content based on the learner&apos;s observed failure patterns, the complexity of tasks performed, and the contexts involved. This is one of the few areas where the AIMediation is granted controlled generative privilege — within a defined template scaffold. 5. Task Architecture Tasks are the atomic unit of the IWSTGS system. All system intelligence — evaluation, progression, adaptation, and profiling — flows from and through tasks. 5.1 The Umbrella Project Model Each simulation session is built around a complex, realistic Umbrella Project — a full software engineering project that mirrors real-world delivery. The project is used to: Provide the context for all tasks assigned during the session. Define the roles required (and thus role enrolment options for learners). Establish the full task dependency map, sequencing logic, and competence coverage. 5.2 Task Components Every task in the system contains the following defined properties: Task Property Description Task ID Unique identifier. Used for branching, tagging, and profile tracking. Task Domain The expert domain this task belongs to (e.g., backend, DevOps, QA, system design). Role Mapping The role(s) this task is assigned to within the project. Competence Dimensions One or more of the six software engineering competence dimensions this task targets. Concepts &amp; Knowledge CS/software engineering concepts, topics, and theoretical knowledge required. Tools Specific tools, frameworks, or technologies referenced or required. CAC Levels The Complexity, Autonomy, and Context Fidelity levels at which this task can be presented. Answer Families Defined ranges of weak-to-strong expected submission patterns per CAC level. Criteria Tiered evaluation criteria mapped to CAC levels. Dependency Map Prerequisite tasks and tasks this task unlocks. Consequence Branch Linked consequence task(s) triggered on failure. Suggestion Branch Linked suggestion task(s) triggered by habit/pattern detection. 5.3 Task as the Source of All Definitions Concepts, tools, and competence dimensions are NOT defined globally in the system. They are defined within each task. This means: The system does not prescribe a fixed global curriculum or vocabulary. A runtime inference layer aggregates concept tags across tasks to generate learning paths and concept mastery tracking. Learning path generation is dynamic: the system identifies what concepts a learner has not demonstrated mastery of, and routes them to tasks in the pool that target those concepts at the appropriate difficulty. 5.4 Concept Tag Index Although concepts are defined inside tasks, a secondary concept tag index is maintained at the system level. This index: Maps concept tags to all tasks that reference them. Enables the learner profile to aggregate evidence across tasks (e.g., &apos;Learner has encountered database transactions in 3 tasks: met criteria in 2, partial in 1&apos;). Is populated automatically when tasks are authored or updated. Can be updated with novel concept tags when AIMediation recommends them based on strong unique learner submissions. 6. Competence Dimensions IWSTGS evaluates learner competency across six core software engineering competence dimensions. These dimensions are universal across tasks, though the specific criteria and depth of evaluation vary by task domain and CAC level. 6.1 The Six Core Dimensions # Dimension Core Question Observable Indicators 1 Problem Analysis &amp; Decomposition Does the learner understand the problem before solving it? Requirements identification, constraint acknowledgment, sub-problem breakdown, ambiguity navigation. 2 Design &amp; Architecture Does the learner make justifiable structural decisions? Separation of concerns, pattern selection, scalability consideration, trade-off articulation. 3 Implementation &amp; Coding Does the learner translate design into working, quality code? Correctness, code structure, readability, error handling, adherence to standards. 4 Testing &amp; Quality Assurance Does the learner verify and validate their work? Test coverage, test strategy, edge case identification, defect reporting. 5 Debugging &amp; Problem-Solving Does the learner identify and resolve failures methodically? Root cause isolation, hypothesis testing, log interpretation, fix verification. 6 Communication &amp; Documentation Does the learner communicate their work clearly and professionally? Code comments, technical documentation, decision justification, clarity of explanation. 6.2 Dimension Weighting by Role Not all dimensions are equally weighted for all roles. Role enrolment defines a weighting schema that influences final qualification assessment. For example: Backend Engineer: System Design and Implementation carry higher weight. QA Engineer: Testing &amp; QA and Debugging carry higher weight. Technical Lead: All dimensions weighted, with Communication &amp; Documentation elevated. Weighting schemas are defined per role in the system configuration and applied only at the final profile evaluation stage. 7. Task Complexity, Autonomy &amp; Context Fidelity (CAC) Model Every task is presented to a learner at a specific intersection of three dimensions: Complexity, Autonomy, and Context Fidelity. Together, these three form the CAC model — the primary mechanism by which the system adapts task presentation to a learner&apos;s current level. 7.1 Dimension Definitions Dimension Definition &amp; What Changes Complexity The scope and interdependencies of the problem. Changes the number of components involved, the breadth of the solution space, and the depth of engineering judgement required. Autonomy The level of scaffolding and guidance provided. Changes how much direction, hints, structure, and framing the learner receives when engaging with the task. Context Fidelity The realism and ambiguity of the scenario framing. Changes how closely the task mirrors a real professional situation, including its constraints, stakeholder context, and ambiguity. 7.2 CAC Levels Level Label Description 1 Low Narrow scope, high guidance, clearly framed scenario. Suitable for junior learners or introduction to a new concept. 2 Mid Moderate scope, moderate guidance, some contextual realism and ambiguity. 3 High Broad scope, minimal guidance, high realism and ambiguity. Requires independent reasoning and decision-making. 7.3 CAC Adjustment Rules The CAC dimensions are adjusted independently, not simultaneously. The following order governs escalation: CAC Adjustment Priority Order Step 1 — Adjust Autonomy first: Reduce guidance before increasing complexity. Withdrawal of scaffolding is the gentlest form of challenge increase. Step 2 — Adjust Context Fidelity: Increase realism and ambiguity once learner performs well with reduced guidance. Step 3 — Adjust Complexity: Increase scope and interdependencies only after consistent performance at current complexity level. Complexity escalation is structural and earned. Note: Complexity escalation typically occurs at scenario transitions, not within a single scenario. 7.4 Scaffolding on Complexity Escalation When a learner is introduced to a complexity level they have not previously experienced (evidenced by their profile rank), Autonomy is automatically reduced (guidance increased). This implements the Scaffolding principle — the learner is supported through the transition before support is gradually withdrawn. 7.5 Progression Vector Progression is a multi-dimensional vector, not a single line. A learner&apos;s profile tracks each CAC dimension independently. It is valid and expected for a learner to: Progress in Complexity while temporarily regressing in Autonomy (more support given for harder problems). Plateau in Complexity while advancing in Context Fidelity (same problem scope, greater realism). True competence is defined as: High Complexity + High Autonomy + High Context Fidelity + Meeting all high-tier core criteria. 8. AIMediation Engine — Roles, Rules &amp; Boundaries The AIMediation Engine is the intelligent layer of the system responsible for evaluation, pattern recognition, hint generation, and certain runtime task creation. It operates within strictly defined boundaries. The system&apos;s rules always take precedence over AI judgement. 8.1 Deterministic Functions (Rule-Based, No AI Discretion) Task assignment logic: Rank ? CAC level mapping. Consequence task triggering: failure threshold ? consequence task route activation. Role qualification matching: dimension profile ? role threshold comparison. Rank escalation and de-escalation thresholds. Mismatch detection: submission quality vs. declared entry level. 8.2 AI-Interpreted Functions (Guided by System Rules) Submission evaluation: the AI checks submissions against pre-defined criteria. It does not evaluate freely. Pattern recognition: detecting bad habits, recurring gaps, and dimension-specific weakness across submissions. Hint and suggestion generation: the AI generates guidance within defined template structures. Answer family pattern matching: mapping submission content to the defined answer family spectrum. Concept and keyword extraction from novel strong submissions (for system improvement recommendations only, not automatic update). 8.3 Controlled Generative Privilege The AIMediation is granted generative privilege in one specific case: Controlled Generative Privilege: Diagnostic Consequence Tasks When a rank review is triggered for an experienced learner who fails beyond the failure threshold, the AIMediation may generate a Diagnostic Consequence Task using a pre-defined template scaffold. The AI fills in task content based on: observed failure patterns, complexity of tasks attempted, and task contexts. The template scaffold constrains format, evaluation criteria structure, and answer family requirements. The AI does not define criteria or rubric independently — it instantiates criteria from the template. 8.4 Conflict Resolution Rule If the AIMediation evaluation result disagrees with the rubric or produces a result that cannot be confidently mapped to any defined criterion: The rubric always wins. The system never silently overrides its own rubric with AI judgement. The evaluation is flagged as &apos;uncertain evaluation&apos;. The system either triggers a follow-up clarification prompt to the learner, or escalates to a human reviewer queue. 8.5 AIMediation Trigger Thresholds Trigger Condition AIMediation Response Learner fails same dimension 3+ times Identify failure type (knowledge gap vs. strategy gap). Assign targeted hint or inject dimension-targeted task in next scenario. Learner demonstrates a recurring bad habit Flag habit on profile. Queue a Suggestion Task. Submission quality significantly exceeds current rank level Flag mismatch. Surface escalation prompt or auto-escalate sub-level. Submission cannot be confidently evaluated Mark as &apos;uncertain&apos;. Trigger follow-up prompt or human review. 3+ strong novel submissions contain new concepts not in tag index Generate recommendation for system curator to update concept tag index and relevant task criteria. 9. Submission Evaluation Framework All learner submissions are evaluated across three layers. This multi-layer model allows the system to distinguish between different types of gaps and evaluate both functional correctness and engineering judgement. 9.1 The Three Submission Layers Layer Name What It Captures Failure Signal 1 Text Explanation Learner&apos;s understanding of the problem, their reasoning, and decision justification. Wrong logic in explanation despite correct code ? strategy gap. 2 Artifacts / Documents Planning documents, diagrams, documentation, architecture notes. Missing or weak artifacts with correct code ? documentation/design gap. 3 Code / Implementation The functional output: code, scripts, configurations. Wrong implementation despite correct explanation ? execution gap. 9.2 Knowledge Gap vs. Strategy Gap Detection If text explanation contains correct logic but implementation is wrong: Strategy/execution gap. The AIMediation provides process-oriented or approach-level hints. If both text explanation and implementation are incorrect or incomplete: Knowledge gap. The AIMediation provides conceptual or explanatory hints. If text explanation is wrong but implementation is accidentally correct: Correctness is not confirmed. A follow-up clarification prompt is triggered. 9.3 Follow-Up Prompt at High Complexity At high complexity tiers, the AIMediation may issue a single follow-up prompt (e.g., &apos;Why did you structure it this way?&apos;) after a submission. This serves two purposes: It reveals whether submission correctness was understood or accidental. It acts as a passive anti-copy mechanism without accusing the learner. Follow-up prompts are defined in a template library. The AIMediation selects the appropriate template based on task domain and submission type. 10. Answer Families &amp; Criteria Definition Each task contains a spectrum of expected submission patterns ranging from weak to strong. These are called Answer Families. Criteria are the measurable standards against which submissions are evaluated, and are tiered by CAC level. 10.1 Answer Families Answer families are not exhaustive lists of correct solutions. They are defined patterns of response quality that the AIMediation uses to locate a learner&apos;s submission on the competency spectrum. Family Tier Description Weak Submission shows minimal understanding. Key concepts absent or misapplied. Little or no justification. Incorrect or incomplete implementation. Developing Submission shows partial understanding. Core concepts present but misapplied or incomplete. Some justification present. Implementation partially correct. Competent Submission meets the criteria for the current CAC level. Concepts applied correctly. Justification present. Implementation functionally correct. Strong Submission exceeds expectations for the current CAC level. Additional depth, foresight, or engineering quality observed. Well-justified with awareness of trade-offs. Expert Submission demonstrates mastery. All criteria met at the highest tier. Architectural quality evident. Submission quality would be appropriate at a higher rank level. 10.2 Criteria Tiers Criteria are defined per task per CAC complexity level. The same competence dimension is evaluated at different depths depending on the complexity tier. This is not the same as interpreting one criterion differently — they are genuinely different criteria. Example: System Design Dimension — Criteria Across Complexity Levels Low Complexity: Identifies the main components needed for the feature. Demonstrates understanding of separation of concerns at a module level. Mid Complexity: Identifies component interactions and dependencies. Justifies technology/pattern choices with rationale. High Complexity: Demonstrates architectural decision-making across distributed components. Addresses scalability, fault tolerance, and consistency trade-offs. 10.3 Architectural Criteria and Rank Criteria for low-complexity tasks do not include architectural quality indicators. This is by design: junior-rank learners are not assigned architectural tasks, mirroring real-world team structures where juniors are not responsible for system-level design decisions. 10.4 Hybrid Evaluation Model Answer families use a hybrid definition approach for scalability: Core criteria and concept tags are manually defined per task. These are the authoritative evaluation anchors. The AIMediation checks submissions against these criteria — it does not infer correctness freely. When a learner submits a novel strong answer that is not covered by existing answer families but meets all criteria, the AIMediation flags it and recommends it as candidate content for updating the task&apos;s answer families. This enables the system&apos;s evaluation quality to improve over time from real learner submissions. 11. Task Progression Logic Task progression determines the order in which tasks are assigned, the difficulty trajectory a learner follows, and how the system responds to both strong and weak performance. 11.1 Core Task Sequence Within each scenario, learners complete a sequence of core tasks. Core tasks are the primary deliverables of the scenario. They are sequenced based on the dependency map of the Umbrella Project. 11.2 Progressive Difficulty Core tasks must increase in difficulty as the learner progresses. However, this is not a rigid step-by-step escalation. The system may: Vary which CAC dimension escalates first (following the priority order in Section 7.3). Introduce different task types targeting different competence dimensions to prevent monotony. Route learners with dimension-specific weaknesses to dimension-targeted tasks in subsequent scenarios. 11.3 The &apos;Move Forward&apos; Rule The system does not require a learner to achieve the strongest possible answer before progressing. After a core task and its consequence branch (maximum one consequence task per core task branch), the learner advances to the next core task regardless of final submission quality. The Move Forward Rule A learner will not repeat the same task indefinitely until achieving a perfect submission. After 1 consequence task attempt per core task branch, the learner moves forward. Unresolved weaknesses are recorded on the learner profile with a specific gap flag. The profile accumulates evidence truthfully. The system does not hide partial competence. This mirrors real-world professional environments where learning continues across projects. 11.4 Dimension-Targeted Task Injection When the AIMediation observes persistent weakness in a specific dimension across a full scenario (core + consequence + any diagnostic tasks), the next scenario assigned to the learner should include tasks that specifically target that dimension. This targeted injection: Is separate from the regular consequence task mechanism. Operates at the scenario selection level, not the individual task level. Allows the learner to continue advancing in other dimensions while receiving focused practice in the weak one. 12. Consequence Tasks Consequence tasks are remedial tasks triggered when a learner fails a core task. They provide an additional opportunity to engage with the same competence area before moving forward. 12.1 Trigger Conditions A learner fails a core task submission (submission does not meet the minimum competent threshold for the current CAC level). Failure is confirmed after evaluation across all three submission layers. 12.2 Consequence Task Properties Property Value / Rule Quantity per branch Maximum 1 consequence task per core task branch. Complexity level Set at runtime according to learner&apos;s current rank (same as core task complexity). Autonomy level Slightly reduced from the failed core task (more guidance provided). Context Fidelity Same as the failed core task. Goal Address the root issue observed in the failed submission — not repeat the same task in a different form. Architectural criteria Not included if learner is at junior rank. 12.3 Consequence Task and Compounding Weakness A learner who fails a consequence task still moves forward. The unresolved weakness is recorded on the profile. The system&apos;s goal is not to block progress but to produce a truthful competency profile and ensure the learner has been exposed to the problem at least twice. 12.4 Root Cause Targeting Consequence tasks must address the specific failure type identified. The AIMediation routes the consequence task selection based on the gap type (knowledge gap ? conceptual consequence task; strategy gap ? process/approach-focused consequence task). This prevents the system from simply presenting the same failure situation in a cosmetically different form. 13. Suggestion Tasks Suggestion tasks are proactive tasks triggered by the AIMediation when it detects a learner habit or behavioural pattern that is not a direct failure in any dimension but represents a tendency that will limit effectiveness at higher levels. 13.1 Distinction from Consequence Tasks Characteristic Consequence Task vs. Suggestion Task Trigger Consequence: failure on a core task. | Suggestion: detected habit or pattern (not necessarily a failure). Timing Consequence: immediately after a core task failure. | Suggestion: may be queued for a future scenario or injected between scenarios. Complexity Consequence: same as core task. | Suggestion: may introduce a higher complexity as a challenge/extension. Template Consequence: task-specific, linked to core task branch. | Suggestion: habit-agnostic template, reusable across learners with different habits. 13.2 Distinction from Diagnostic Tasks Characteristic Diagnostic Task vs. Suggestion Task Domain of Operation Diagnostic: operates in diagnostic scenarios to establish initial rank. | Suggestion: operates within active project scenarios. Purpose Diagnostic: rank determination. | Suggestion: habit correction or capability extension. CAC Setting Diagnostic: fixed at mid-level. | Suggestion: set at runtime per learner rank, may escalate for extension. Reusability Both use skill-agnostic templates that can be re-instantiated by AIMediation for different learners. 13.3 Suggestion Task Scope Suggestion tasks can be corrective (addressing an identified bad habit) or extensional (challenging a high-performing learner with a habit that will become a problem at the next level). The AIMediation must specify in the suggestion task record which type it is, and this classification is visible on the learner profile. 14. Diagnostic Tasks (Runtime-Generated) Diagnostic tasks in the context of active project scenarios (distinct from diagnostic scenario tasks at entry) are runtime-generated tasks produced by AIMediation when a rank review is triggered for an experienced learner who has failed beyond threshold. 14.1 Template Structure Diagnostic consequence task templates are defined as: Complexity-agnostic: the same template can be applied at any complexity level. Autonomy-agnostic: guidance level is set by AIMediation at runtime based on failure pattern. Context-agnostic: the task context is filled in by AIMediation based on the project and failure area. 14.2 AIMediation Input for Generation When generating a diagnostic consequence task, the AIMediation is given: The learner&apos;s observed failure pattern (dimension, sub-criterion, failure type). The complexity level of the tasks the learner has been performing. The contextual framing of the current scenario. The template scaffold that defines format and evaluation structure. The AIMediation instantiates the task within the template. It does not create tasks with undefined criteria — the criteria structure is always template-derived. 15. Learner Profile &amp; Final Competency Graph The learner profile is the primary output of a learner&apos;s engagement with the system. It is a dynamic, multi-dimensional record that grows throughout the simulation and culminates in a final competency graph. 15.1 Profile Components Profile Attribute Description Current Rank Learner&apos;s current rank tier and sub-level. Updated dynamically. Dimension Scores Per-dimension performance rating, tracked across all tasks. Expressed as a tier rating (basic / intermediate / advanced) not a numerical score. Unresolved Gaps Flags for dimensions where the learner failed core and consequence tasks. Includes specific sub-criterion that was not met. Concept Mastery Map Aggregated evidence of concept engagement: encountered, partially met, mastered. CAC Trajectory History of Complexity, Autonomy, and Context Fidelity levels at which learner has operated. Task History Ordered list of tasks attempted, submission outcomes, and time-to-submission data. Habit Flags Detected patterns and habits surfaced by AIMediation. Includes whether suggestion task was issued and outcome. Escalation/De-escalation Events Record of all rank changes and the performance data that triggered them. 15.2 Final Competency Graph At the end of a simulation session, the learner&apos;s profile generates a Final Competency Graph — a radar/web chart representation of their performance across all six competence dimensions at the depth tiers reached. The graph presents: Each of the six dimensions as an axis. The depth tier (basic / intermediate / advanced) reached in each dimension. Visual distinction between &apos;met&apos;, &apos;partially met&apos;, and &apos;unresolved gap&apos; per dimension. 15.3 Profile Interpretation: Not a Flat Rank The final profile does not collapse into a single Junior/Mid/Senior label. A learner may be advanced in Implementation but basic in Design. This is a specialisation pattern, not a rank. The profile communicates this accurately: Role qualification is assessed against the weighting schema for the enrolled role. Strengths and gaps are surfaced explicitly with specific dimension and tier details. The learner is informed of which roles they qualify for and why they do or do not meet requirements for others. 16. Role Qualification Logic At the end of a simulation session, the system determines which professional roles the learner qualifies for, based on their final competency graph and the role weighting schemas. 16.1 Qualification Assessment Each role has a defined minimum threshold for each competence dimension, expressed as a required depth tier. The learner&apos;s profile dimension ratings are compared against the role threshold matrix. A learner qualifies for a role if they meet or exceed the threshold for all required dimensions, accounting for the role&apos;s weighting schema. Unresolved gaps in dimensions that are core to a role will disqualify the learner from that role. 16.2 Qualification Output The system produces a role qualification report that states: Roles the learner qualifies for, with the qualifying dimensions listed. Roles the learner does not qualify for, with the specific dimension(s) and tier(s) not met. Recommended next-focus areas for learners who narrowly missed qualification for a target role. 16.3 Specialisation Recognition The system recognises and surfaces specialisation patterns. A learner who is strong in system design but weak in debugging will be directed toward architect-adjacent roles and advised to build debugging competency before seeking roles where it is core. This is more useful to the learner than a flat &apos;Junior&apos; label. 17. Concept Tagging &amp; Knowledge Mapping IWSTGS is designed to build on foundational knowledge from university and institutional education. The concept tagging system connects task-embedded knowledge to established CS and software engineering curricula. 17.1 What Concept Tags Cover Software Engineering Concepts: design patterns, SOLID principles, system architecture, API design, etc. Computer Science Fundamentals: data structures, algorithms, networking, databases, operating systems, etc. Tools &amp; Technologies: specific frameworks, languages, CI/CD tools, testing frameworks, version control, etc. Professional Practice: Agile/Scrum, code review, technical documentation, estimation, etc. 17.2 Tagging Rules Tags are defined inside the task, not globally. The concept tag index aggregates tags from all tasks at the system level for cross-task mastery tracking. Evidence of meeting criteria is the observable indicator of concept mastery — not self-report or multiple choice. A concept is considered &apos;mastered&apos; on the profile when the learner meets the competent or higher answer family tier in at least two tasks that tag that concept. 17.3 University Knowledge Bridge Tasks are designed so that learners who have completed relevant university modules have sufficient foundational knowledge to engage with the task at low complexity. The system explicitly maps which university-level concepts are prerequisites for each task. This ensures: The system never assumes knowledge the learner cannot have been exposed to. The gap between institutional education and industry practice is made explicit and addressable. Learners who lack expected prerequisites are identified early (during diagnostic scenarios) and routed appropriately. 18. System Control vs. AI Flexibility Boundaries A core design principle of IWSTGS is maximum system control over the AIMediation. The following table summarises the full boundary map. System Function Control Type Task assignment rules (rank ? CAC level) Deterministic / Rule-based Consequence task triggering Deterministic / Rule-based Role qualification matching Deterministic / Rule-based Rank escalation and de-escalation Deterministic / Rule-based Mismatch detection thresholds Deterministic / Rule-based CAC adjustment priority order Deterministic / Rule-based Submission evaluation against criteria AI-interpreted (criteria-anchored) Learner pattern and habit recognition AI-interpreted (template-constrained) Hint and suggestion content generation AI-interpreted (template-constrained) Answer family pattern matching AI-interpreted (criteria-anchored) Diagnostic consequence task generation AI-interpreted (template-constrained, controlled privilege) Concept tag recommendation from novel submissions AI-interpreted (recommendation only, not auto-applied) Follow-up clarification prompt selection AI-interpreted (template-library constrained) Governing Principle The AIMediation is an evaluator, not an authority. This ensures the system&apos;s behaviour is predictable, auditable, and improvable. 19. Research Backing &amp; Theoretical Foundations The IWSTGS design is grounded in established educational theory, cognitive science, and software engineering education research. The following frameworks directly inform the system&apos;s logic. 19.1 Zone of Proximal Development (Vygotsky, 1978) The concept of ZPD — the space between what a learner can do independently and what they can do with support — underpins the Autonomy dimension and the Scaffolding-on-escalation rule. IWSTGS deliberately operates in the learner&apos;s ZPD: tasks are chosen to stretch the learner just beyond their independent capability, with guided support that is gradually withdrawn. 19.2 Scaffolded Instruction (Wood, Bruner &amp; Ross, 1976) Scaffolding theory supports the system&apos;s rule that Autonomy is reduced when Complexity escalates. The temporary support given to learners on new complexity levels mirrors the scaffolding and fading model in educational theory. 19.3 Deliberate Practice (Ericsson et al., 1993) Deliberate practice theory holds that skill development requires targeted practice with feedback at the edge of current capability — not repetition of already-mastered skills. IWSTGS implements this through: adaptive CAC adjustment, dimension-targeted task injection, and the move-forward rule (preventing over-repetition of already-attempted challenges). 19.4 Authentic Assessment (Wiggins, 1989; Newmann &amp; Archbald, 1992) Authentic assessment theory argues that meaningful evaluation requires real-world tasks with genuine complexity, not abstracted exercises. IWSTGS&apos;s project-based structure, role enrolment, context fidelity dimension, and three-layer submission model all reflect authentic assessment principles. 19.5 Competency-Based Education (CBE) CBE frameworks support the system&apos;s dimensional profiling approach. Rather than time-based progression, IWSTGS advances learners based on demonstrated competency across defined dimensions — consistent with CBE&apos;s emphasis on evidence-based qualification. 19.6 Formative vs. Summative Assessment The system uses ongoing task evaluation as formative assessment (guiding learning through feedback and consequence tasks) and the final competency graph as summative assessment. This dual-mode approach is well-supported in educational assessment literature as producing better learning outcomes than summative-only evaluation. 19.7 Mastery Learning (Bloom, 1968) The consequence task system and the &apos;move forward&apos; rule are influenced by mastery learning theory. The system allows learners to engage with material at depth before advancing, without requiring perfection, and records partial mastery truthfully — supporting Bloom&apos;s finding that most learners can achieve high outcomes given appropriate time and feedback. 20. Glossary Term Definition AIMediation The intelligent evaluation and adaptation engine of IWSTGS. Operates within system-defined boundaries. Answer Family A defined pattern of submission quality (from weak to expert) used to locate a learner&apos;s submission on the competency spectrum. Autonomy (CAC) The degree of scaffolding and guidance provided with a task. Low autonomy = more guidance; high autonomy = independent work. CAC Model Complexity, Autonomy, and Context Fidelity — the three adaptive dimensions used to calibrate task presentation to learner level. Competence Dimension One of the six core domains of software engineering competency evaluated by the system. Complexity (CAC) The scope and interdependency level of a task&apos;s problem space. Concept Tag Index A system-level index that maps concept tags defined in tasks to enable cross-task mastery tracking. Consequence Task A remedial task triggered by failure on a core task. Maximum one per core task branch. Context Fidelity (CAC) The degree to which a task scenario mirrors real-world professional conditions, including ambiguity and constraints. Core Task A primary scenario task that represents a project deliverable. Forms the backbone of the task sequence. Diagnostic Scenario A mid-complexity scenario used to establish a learner&apos;s initial rank. CAC levels are fixed, not runtime-adjusted. Diagnostic Consequence Task A runtime-generated task created by AIMediation using a template scaffold when a rank review is triggered. Dimension-Targeted Task A task injected in a subsequent scenario to address a specific competence dimension weakness identified across a full scenario. Gap Flag A profile attribute marking an unresolved competence gap after a learner has moved past a task branch. Rank A tiered attribute on the learner profile governing task assignment and profile interpretation. Includes sub-levels within each tier. Role Qualification The final assessment of which professional roles a learner meets the competency thresholds for. Suggestion Task A proactive task triggered by detection of a learner habit or pattern that will limit effectiveness at higher levels. Umbrella Project The complex, realistic software engineering project that frames all tasks in a simulation session. ZPD Zone of Proximal Development — the learning space just beyond a learner&apos;s independent capability, supported by scaffolding.
