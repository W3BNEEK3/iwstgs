The Three-Tier Content Hierarchy: Project ? Scenario ? Task Content in IWSTGS is organised in three tiers. Each tier contains and contextualises the tier below it. This hierarchy is the most important structural addition in v2.0. The Three-Tier Content Hierarchy PROJECT — The Umbrella. Defines the client, the business problem, the constraints, the stakeholders, and the tech context. Sets the stage for everything below it. ? SCENARIO — The Chapter. A container for a set of related tasks. Defines the narrative moment: who the learner is, what just happened, what they&apos;ve been asked to do. Carries scenario-specific reference materials (emails, incomplete docs, Slack messages). ? TASK — The Work Item. A single deliverable within a scenario. Defines what to produce, how it&apos;s evaluated, what criteria apply, what concepts are involved, what guidance is available. Tier Analogy What It Answers Project The client engagement What project are we building? Who is the client? What are the constraints? What is the tech context? Scenario The sprint / work moment What is happening right now? What has the learner just been asked to do? What documents and communications are available to them? Task The ticket / work item What specific deliverable is the learner producing? How will it be evaluated? What criteria apply at what depth? Scenarios serve a function that neither the project nor the task can serve alone. The project gives context that is too high-level for moment-to-moment work. The task gives specific deliverables but no narrative situation. The scenario bridges them: it creates the professional situation the learner is stepping into when they begin a task sequence. 4. Project Template — Updated Schema The following fields are added or changed from v1.0. Fields that are unchanged are not repeated here — refer to v1.0 Section 3.1. 4.1 New Fields Field Description / Rule stakeholders (JSONB array) Array of stakeholder objects: {name, role, priority (high/medium/low), concern}. Each stakeholder represents a named person in the project&apos;s business context. Used by scenario narrative and by AIMediation when evaluating communication-dimension submissions. High-priority stakeholders are referenced in scenario situation_triggers. overarching_constraints (JSONB array) Typed constraint objects: {type (budget/timeline/technical/regulatory), description}. These are project-level constraints that all tasks in the project must be aware of. The AIMediation references these when evaluating whether learners have correctly identified constraints in their submissions. tech_context (JSONB) Object containing: {existing_stack (string array), team_size (integer), deployment_environment (string), special_requirements (string)}. Feeds context fidelity at the scenario and task level. difficulty_level (ENUM) beginner | intermediate | advanced. Presentation-only field for the learner-facing project catalogue. Does not influence task CAC settings, which are set by the engine at runtime. 4.2 Removed Fields Removed Field Reason ownership_type Redundant. If organisation_id is null, the project is a platform default. No separate field needed. 5. Scenario Template — New Schema The scenario is a new table: scenario_template. It is owned by the Simulation bounded context. It sits between project_template and task in the content hierarchy. 5.1 Full Scenario Schema Field Description / Rule id (UUID) Primary key. project_id (UUID) FK to project_template. sequence_order (SMALLINT) Order of this scenario within the project. Determines the sequence in which scenarios are assigned to learners. title (VARCHAR 300) Display title for the scenario. E.g., &apos;Sprint 0 — Requirements Analysis and Architecture Proposal&apos;. narrative_context (TEXT) The backstory and situation the learner is stepping into. Written in second-person professional voice. Describes recent events, team context, and why the work is needed. This is the primary context fidelity mechanism at the scenario level. situation_trigger (TEXT) The specific message, event, or communication that kicks off the scenario work. Can be a Slack message, email, meeting summary, or incident report. Presented to the learner at scenario start before tasks are revealed. Drives immersion and realism. learner_role_label (VARCHAR 200) The job title label for the learner&apos;s role in this scenario&apos;s narrative. E.g., &apos;Lead Backend Developer&apos;. This is a narrative presentation label, not a system role. The actual role is set at project enrolment. reference_materials (JSONB array) Array of scenario-specific documents: {type (document/email/slack/report/ticket), title, content}. These are NOT in the Artifact Vault — they are scenario-level inputs that set up the task work. E.g., an incomplete requirements doc, a client email, a prior developer&apos;s notes. primary_dimension_labels (TEXT array) Array of task-specific dimension labels that are prominent in this scenario&apos;s tasks. Informational only — used by content authors to ensure dimension coverage. Not used by the engine directly. default_autonomy_level (ENUM) low | mid | high. The default Autonomy (support level) for tasks in this scenario. Tasks may override this. Maps directly to the CAC Autonomy dimension. Replaces the v1.0 support_level field. is_diagnostic (BOOLEAN) True = this scenario is a diagnostic scenario used for initial rank assignment. CAC is fixed at mid for all tasks; engine does not adjust at runtime. is_published (BOOLEAN) Controls visibility in the content catalogue. is_active (BOOLEAN) False = retired scenario. Existing sessions continue; no new assignments. 5.2 Fields Discarded from Template Discarded Field Reason task_count Derived value. Count tasks with this scenario_id instead. estimated_duration_minutes The system does not enforce time limits and does not surface duration to learners. May be kept as optional author metadata but is not a system field. difficulty_level Redundant. Difficulty is managed by CAC at the task level and by difficulty_level on the project template for catalogue display. 5.3 How Scenarios Map to the Execution Flow When a learner begins a new scenario, the experience layer presents: The narrative_context as a briefing panel before any tasks are shown. The situation_trigger as the first visible &apos;message&apos; in the simulation environment — framed as a communication the learner has just received. The reference_materials as accessible documents within the scenario workspace (distinct from the Artifact Vault). The first task&apos;s sprint card, unlocked after the learner acknowledges the situation trigger. 6. Task Template — Updated Schema The task schema is significantly extended in v2.0. The following subsections cover each new structural element. 6.0 Core Task Fields (Updated) Field Description / Change from v1.0 scenario_id (UUID) NEW. FK to scenario_template. Tasks now belong to scenarios, not directly to projects. Project is accessed via scenario.project_id. sequence_order (SMALLINT) NEW. Order of this task within its scenario. Replaces the project-level task_pool_ids array ordering. task_brief (TEXT) NEW. The specific instructions given to the learner. Written in second-person. Includes the deliverable expectation and the audience context. This is what the learner reads before starting work. code_execution_config (JSONB/null) NEW. Null if the task does not require code execution. When populated: {language, entry_point, test_cases, docker_image}. The Submission context reads this to determine whether to spin up a Docker container for this submission. model_response_summary (TEXT) NEW. A narrative paragraph describing what a strong (distinguished-tier) submission looks like holistically. Used by AIMediation as a holistic reference in addition to individual criteria. time_limit_minutes (INT/null) Null = no time limit enforced. When set, the experience layer shows a countdown timer but submission is still accepted after timeout (timeout is flagged, not blocking). 6.1 Expected Deliverables (replaces fixed three-layer model) In v1.0, all tasks were assumed to require all three submission layers (text, artifact, code). This was incorrect. The expected_deliverables array on the task defines which submission layers are active for this specific task. Deliverable Type Maps to Submission Layer Notes written_explanation Layer 1: Text The learner&apos;s written reasoning and justification. Required on almost all tasks. artifact Layer 2: Artifacts Planning documents, diagrams, architecture notes. Required on design tasks. code Layer 3: Code Functional implementation. Only present when code_execution_config is also set. diagram Layer 2: Artifacts Specifically a diagram (UML, ERD, flow). Submitted as a file upload. document Layer 2: Artifacts A structured document output (e.g., requirements analysis report, ADR). Each deliverable has: {type, label, description, is_required}. The submission form in the experience layer renders only the input fields corresponding to this task&apos;s expected_deliverables. A task with no code deliverable does not show a code editor. 6.2 Competence Evaluation Block The competence_evaluation array on a task defines how the task is scored. Each entry in the array covers one competence dimension and contains: the dimension label, the weight (0.0–1.0, all weights must sum to 1.0), and an array of rubric criteria. Competence Evaluation Block Structure { dimension: &apos;requirements_interpretation&apos;, // task-specific label parent_dimension_id: &apos;dim_001&apos;, // maps to BLD top-level dimension weight: 0.40, // proportion of total task score criteria: [ ... ] // array of rubric_criterion objects } The parent_dimension_id field is new and critical: it links the task-specific dimension label to one of the six canonical BLD competence dimensions tracked on the learner profile. This is how task-level specificity and profile-level aggregation are both preserved. 6.3 Performance Levels (replaces Answer Families) The five-tier answer family model (weak/developing/competent/strong/expert) from v1.0 is replaced by the four-tier performance level model used in actual task templates. These two models represent the same concept; the four-tier version is preferred because it is more established in rubric design literature and more practical for AIMediation detection. Performance Level Description &amp; Threshold Rule Distinguished Exceeds all criteria for the current CAC level. Submission demonstrates depth, foresight, and professional judgement beyond what was required. Maps to the former &apos;expert/strong&apos; tier. Proficient Meets all core criteria for the current CAC level. Submission is correct, complete, and clearly reasoned. This is the competency threshold — submissions at this level or above pass. Maps to the former &apos;competent&apos; tier. Developing Partially meets criteria. Some understanding is present but gaps or vagueness remain. Submission is below threshold — consequence task triggered. Maps to the former &apos;developing&apos; tier. Beginning Does not meet criteria. Fundamental misunderstanding or absence of required analysis. Consequence task triggered. Maps to the former &apos;weak&apos; tier. The pass threshold is Proficient. Developing and Beginning are both failing tiers that trigger consequence tasks. The distinction between them matters for gap type detection: Beginning typically indicates a knowledge gap; Developing typically indicates a strategy or execution gap. 6.4 The claude_detection_hint The claude_detection_hint is a required field on every rubric criterion. It is the single most important mechanism for maintaining control over AIMediation evaluation. It is never shown to the learner. What claude_detection_hint Must Contain What the AI should specifically look for in the submission to confirm this criterion is met. What a surface-level or vague response looks like (so the AI does not over-credit it). What distinguishes tiers from each other for this specific criterion. Any domain-specific knowledge or scenario context the AI needs to evaluate correctly. Examples of strong vs. weak responses where the distinction is non-obvious. The detection hint is what prevents the AIMediation from evaluating freely. Without it, the AI interprets criteria based on general knowledge. With it, the AI evaluates against the specific scenario context, the specific reference materials, and the specific distinctions the task author has defined. 6.5 Knowledge Anchors Knowledge anchors are the replacement for the v1.0 concept_tag system at the task level. They are richer — each anchor connects a concept to a specific application expectation and provides a remediation hint if the learner shows partial understanding. Field Description concept_name Human-readable name of the concept. E.g., &apos;Requirements Engineering&apos;, &apos;NDPR Compliance&apos;, &apos;Non-Functional Requirements&apos;. domain The knowledge domain this concept belongs to. E.g., &apos;Software Engineering&apos;, &apos;Data Privacy and Regulatory&apos;. application_expectation What demonstrating understanding of this concept looks like in this specific task&apos;s context. Not a generic definition — tied to the scenario. is_required (BOOLEAN) False = the concept is not required for a proficient submission but its presence indicates stronger depth. True = absence of this concept understanding is a gap flag. remediation_hint Targeted guidance given to the learner when the AIMediation detects partial understanding of this concept. Directs them toward the concept without simply giving the answer. This is what feeds the AIMediation&apos;s knowledge-gap hint generation. Knowledge anchors with is_required = false are not penalised when absent but are recorded in the learner&apos;s concept mastery map when present. Their remediation_hint is surfaced by AIMediation as a follow-up prompt after the submission is evaluated, not before, so it functions as enrichment rather than scaffolding. 6.6 Guidance Prompts Guidance prompts are pre-authored hints that AIMediation delivers when it detects a learner struggling with a specific dimension. They are part of the system&apos;s controlled AIMediation model — the AI does not generate hints freely; it selects and delivers from a defined prompt library. Field Description trigger_dimension The competence dimension label that must show signs of weakness for this prompt to be triggered. prompt_text The actual text of the hint. Written as a guiding question, not a direct answer. Directs the learner&apos;s attention without revealing the answer. autonomy_level_filter The Autonomy level at which this prompt is shown. A prompt with filter &apos;moderate&apos; (mid Autonomy) is shown at mid Autonomy but not at high Autonomy (where the learner is expected to work without hints). Renamed from support_level_filter in the original template for CAC terminology consistency. Guidance prompts are delivered proactively during the task (before submission) when AIMediation detects inactivity or weak intermediate work. They are also delivered reactively after a developing or beginning submission, selected based on the dimension where the gap was detected. 7. Competence Dimensions — Reconciled Model Two dimension models existed across the documents: the six canonical BLD dimensions and the task-level specific dimension labels in the task templates. These are now unified through a two-level model. 7.1 The Two-Level Dimension Model Level 1 — Canonical Dimensions: The six BLD dimensions tracked on the learner profile. These are the permanent profile-level dimensions. Level 2 — Task-Specific Dimension Labels: Task-level labels that are more specific to the domain and scenario. Each task-level label maps to one parent canonical dimension. Canonical Dimension (BLD) Example Task-Level Labels Notes Dim 1: Problem Analysis &amp; Decomposition &apos;requirements_interpretation&apos;, &apos;problem_scoping&apos;, &apos;constraint_identification&apos; Any task-level label involving understanding, breaking down, or analysing a problem maps here. Dim 2: Design &amp; Architecture &apos;system_design_reasoning&apos;, &apos;architecture_proposal&apos;, &apos;data_model_design&apos; Any label involving structure, decisions about system shape, or design trade-offs. Dim 3: Implementation &amp; Coding &apos;api_implementation&apos;, &apos;database_implementation&apos;, &apos;feature_development&apos; Any label involving writing functional code. Dim 4: Testing &amp; Quality Assurance &apos;test_strategy&apos;, &apos;test_writing&apos;, &apos;quality_review&apos; Any label involving verification, validation, or quality checking. Dim 5: Debugging &amp; Problem-Solving &apos;incident_diagnosis&apos;, &apos;root_cause_analysis&apos;, &apos;performance_investigation&apos; Any label involving identifying and resolving failures or unexpected behaviour. Dim 6: Communication &amp; Documentation &apos;technical_communication&apos;, &apos;documentation_writing&apos;, &apos;stakeholder_reporting&apos; Any label involving written or verbal professional communication. 7.2 Constraint Risk Management — Special Case The task template uses &apos;constraint_risk_management&apos; as a dimension label. This does not map cleanly to a single canonical dimension — it draws on both Dim 1 (problem analysis, identifying constraints) and Dim 2 (design reasoning, risk impact). The resolution: &apos;constraint_risk_management&apos; maps to Dim 1 as its primary parent, with a secondary tag to Dim 2. The rubric criteria within it are split accordingly when aggregating to the learner profile. Rule: Every task-level dimension label must declare exactly one parent canonical dimension. If a label spans two dimensions, assign the primary one and note the secondary as a tag on the rubric criterion, not on the dimension entry. 8. The Four-Layer Submission Model (Revised) The submission model is unchanged in structure but the activation of layers 1–3 is now task-driven rather than always-on. Layer 4 (Planning Snapshot) follows the same rules as v1.0. Layer Name Active When Submission Method 1 Text Explanation is_required = true on a written_explanation deliverable. Active on almost all tasks. Manually entered in submission form. 2 Artifacts / Docs Task has a deliverable of type artifact, diagram, or document. Uploaded or created in the document editor. 3 Code / Implementation Task has a deliverable of type code. code_execution_config is not null. Written in code editor. Optionally executed via Docker. 4 Planning Snapshot planning_layer_active = true on the task. Always passive — never manually submitted. Captured automatically from learner_sprint and learner_backlog_item at submission time. A task like &apos;Analyse the Requirements Document&apos; (from the MedQueue template) has only Layer 1 active (written_explanation with is_required = true). Layer 4 may also be active if the learner was given sprint planning work. Layers 2 and 3 are not active. The submission form shows only a text input — no code editor, no file upload. 10. Planning Layer — Virtual Backlog &amp; Sprint Manager The Planning Layer is unchanged from v1.0. The database model, passive capture rules, rank-differentiated interactions, and evaluation criteria are retained. The following note is added for the scenario layer: Scenario and Sprint Relationship One scenario typically corresponds to one sprint. The sprint goal for a scenario-level sprint should align with the scenario&apos;s overall narrative objective. For diagnostic scenarios (is_diagnostic = true), the Planning Layer is inactive. Sprint board state is not evaluated during diagnostic assessment. Consequence tasks and suggestion tasks injected within a scenario appear in the same sprint as the core tasks that triggered them, not in a new sprint. 11. Gold Standard Reference &amp; CAC-Tiered Rubric Connection The evaluation formula from v1.0 is retained and extended to account for scenario reference materials: Updated Evaluation Formula Evaluation Result = f( Learner Submission (4 layers), Rubric Criteria (CAC-tiered, with claude_detection_hints), Artifact Vault Reference Documents (PRD/SAD — gold standard), Scenario Reference Materials (context docs — for signal detection), Model Response Summary (holistic reference), Knowledge Anchor application expectations ) The AIMediation receives all of these when evaluating a submission. The rubric criteria tell it what to measure. The detection hints tell it how to detect it. The reference documents tell it what the answer should align with. The scenario materials tell it what context signals a strong learner would have picked up. The model response summary gives it a holistic benchmark. 12. After evaluation, AIMediation checks knowledge anchor evidence. For is_required = false anchors: if concept was demonstrated, mastery record updated. If concept was not demonstrated but evidence suggests partial understanding, the anchor&apos;s remediation_hint is surfaced as enrichment feedback to the learner. 10 Profile Update Engine Learner profile updated: dimension tier ratings updated at canonical dimension level, concept mastery map updated, CAC trajectory recorded, gap/habit flags written. If dimension weakness pattern observed across the scenario, suggestion task queued for next scenario. 11 Scenario / Task Transition Engine + Learner If remaining tasks in current scenario: next task card appears on sprint board. If all scenario tasks complete: scenario marked complete, next scenario in sequence_order loaded. Scenario transition triggers scenario onboarding (Step 2) for the new scenario. 13. Decisions Resolved in v2.0 The following open design decisions from v1.0 are now resolved. Decision Resolution Scope warning threshold Defined as a per-rank JSONB object in project_template.velocity_estimate. Each rank tier has a maximum sprint item count. Exceeding it by more than 50% triggers the warning. Authors set the base estimate when creating the project. Suggestion task skip recording Skipping is recorded on the habit_flag record (suggestion_task_id and its status = &apos;skipped&apos;). Skipping a suggestion task for a dimension that is core to the enrolled role contributes a minor note on the final qualification report but does not disqualify. Full disqualification only occurs when dimension_score thresholds are not met. SAD access during diagnostics SAD is withheld during all diagnostic scenarios (is_diagnostic = true). The rank gate on artifact_vault_item applies: SAD not visible until Mid-2+ is assigned post-diagnostic. Consequence card professional framing Consequence cards use the title of the core task prefixed with &apos;Revisit: &apos;. Description is drawn from the task&apos;s task_brief with a single sentence added by AIMediation: &apos;Your team lead has flagged this for additional review.&apos; This framing requires no separate template library for card titles. 20. Open Design Decisions The following questions remain unresolved and require a deliberate design decision before development of the affected components. Decision Area Open Question Options / Considerations Uncertain evaluation human review queue Who is in the human reviewer queue and what is the SLA? What happens to the learner&apos;s session while a submission is in the queue? Requires operational design: internal reviewers, institutional reviewers, or async deferred? The learner session must remain in a &apos;pending review&apos; state with a visible indicator. SLA and reviewer identity model needed before EvalEngine is built. situation_trigger rendering How is the situation_trigger presented in the UI? As a modal on scenario start, an embedded chat-like panel, or a simulated inbox? The rendering model affects how realistic the immersion feels. A simulated Slack or email interface raises context fidelity but increases UI complexity. Decision needed before SimExecution UI is built. Proactive guidance prompt timing At what point during implementation does AIMediation check for dimension weakness and deliver a guidance prompt? Is it on a time trigger, a word-count trigger, or only post-submission? Pre-submission proactive prompts require a partial submission read mechanism. If only post-submission, prompts arrive too late to redirect work in progress. Decision has significant architectural implications for the AIMediation context. Multiple active scenarios Can a learner have more than one scenario in progress simultaneously, or is the system strictly sequential? Strictly sequential is simpler and mirrors a realistic sprint model. Parallel scenarios could be useful for advanced learners. Recommendation: strictly sequential, revisited after launch. Scenario reference material format For scenario reference materials of type email or slack_message, should the system render them with visual formatting (sender, subject, timestamp) or as plain text? Visual formatting significantly raises context fidelity but requires a custom rendering component per material type. Decision needed before the scenario workspace UI is designed.
